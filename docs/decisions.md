# Decision log

One row per decision: what I chose, what else I could have chosen, why, and what it costs. The groups follow the
order of the README. Numbers come from `models/metrics.json` and the two notebooks.

After the first working version I ran two adversarial reviews with Claude Code agents: each finding was checked by a
second agent that tried to disprove it, and the important ones were re-checked by re-running the evidence. They
found two serious mistakes, marked **Revised after review**: de-duplication that hid ~126,000 false alarms a day
(decision 2) and runaway top scores for benign traffic (decision 12). They also found smaller ones, such as inputs
that crashed the API (decision 15).

## Understand the data

| # | Decision | Alternatives | Why | Tradeoff |
|---|---|---|---|---|
| 1 | Drop `src_ip`, `dest_ip`, `src_port` and the timestamps as model inputs | Keep the IPs; encode IP reputation; use the hour of day | Labels come from matching IP IDs against threat intelligence, so `src_ip` alone guesses the label 98% of the time: a model would memorize addresses and fail on new attackers. `src_port` is a random number picked by the sender's OS. Timestamps are 10% corrupt (repaired exactly, used only to sort flows by time), and the hour of a single day would only memorize this day's bursts. | Loses a strong but leaky signal: offline scores are lower, but honest. Time patterns that do repeat (for example nightly scans) are not used. |
| 2 | **Revised after review.** Drop only **exact duplicate rows** (1,039 logging copies); keep repeated flows | First version: drop rows identical in every model input (1.47M rows left) | Repeated flows are real traffic, and how often a pattern occurs matters. An empty one-packet TCP flow to an ephemeral port is 95% benign, but de-duplication kept 49 benign rows against ~4,200 bad ones, so the model learned "99% bad". It flagged **126,136 benign flows** on the day, while the de-duplicated test reported ~92 false alarms a day. Caught by scoring every raw flow with the saved model. | The same flow can be in train and test, as in production. Checked: recall on repeated test flows (95.3%) is lower than on new ones (97.1%), so the score is not memory. |
| 3 | Say the data's limits openly | Claim the scores hold in general | The "IP" columns are network numbers, not machines (786 is JANET, the UK academic network; 15169 is Google). 99.0% of benign flows have both ends inside the monitored network, and labels match either end of a connection. The model largely learns "this network's internal traffic vs. internet traffic". | Lower-sounding claims, but ones a reader can trust. The model must be retrained and re-tested before it is used on another network. |

## Business framing

| # | Decision | Alternatives | Why | Tradeoff |
|---|---|---|---|---|
| 4 | **Target: "not benign" = 1** (malicious + outlier), benign = 0; recall reported for each label | Literal "outlier vs rest"; a 3-class model | This is intrusion detection, so known attacks must be caught. With "outlier vs rest", malicious traffic would count as normal and the model would be punished for flagging real attacks. Malicious and outlier traffic also look the same (8,728 groups of identical flows carry both labels). | It does not say *which* kind of bad traffic a flow is; a second model could. The API keeps the brief's field name, `is_outlier`. |
| 5 | **Success metric: recall inside an alert budget** of 0.01% false positives, about 157 false alarms a day | Accuracy; PR-AUC; F1; a 1% budget | "Always benign" is already 80% accurate, so accuracy says nothing. The budget is a business choice: ~157 a day is what a small team can review, while 1% would allow ~15,700. PR-AUC is reported but hides the operating point: the depth-4 tree has PR-AUC 0.963 and catches only 23% inside the budget. | The model choice depends on the budget. The budget limits false alarms only: the ~377,000 bad flows a day that are correctly flagged are grouped into incidents per source. |
| 6 | **Speed budget:** one process scores at least **4,500 flows a second** | No speed requirement; a single-flow latency target | Flow records arrive after a connection ends, so this is near-real-time scoring: throughput and time to alert matter, not single-flow latency. 4,500 is 10x the busiest minute in the data (26,695 flows at 17:01 UTC, ~445 a second). | It excludes no model today (all score at least ~75,000 flows a second in batches), but it would stop a much heavier one. Single-flow latency (~9 ms) is reported, not used. |

## Model development

| # | Decision | Alternatives | Why | Tradeoff |
|---|---|---|---|---|
| 7 | All preprocessing inside the saved pipeline: `log1p` + scaling for the 8 numbers; one-hot `proto`; `dest_port` grouped (service ports, ephemeral ports merged, rare ports sharing one column, plus the port range); unseen values never crash | Separate preprocessing for training and the API; one-hot all 20,409 ports; target encoding | One object transforms data the same way in training and serving (no train/serve skew). `log1p` tames heavy tails and keeps zeros at zero. Ephemeral ports are random reply ports, so they count as one value. 11 service ports plus "no port" and "ephemeral" cover 98% of rows: 31 columns instead of 20,000. | Rare ports lose their identity. Coefficients and tree splits are in scaled log units (notebook 02 translates the tree's splits back). |
| 8 | **Split 60/20/20, stratified:** fit on train, choose each threshold and the model on validation, use the test set once | 80/20 with thresholds from cross-validation (earlier version); choosing on test | Validation keeps every choice away from the test set. The first cut is the same 80/20 as before, so the test set (392,870 flows) did not change and old and new results compare like with like. | 60% instead of 80% for training (the served model's recall stayed at 96.5%). The budget allows only 31 false alarms on validation, so thresholds are a little noisy, and coarse models carry them less well to test (port lookup: ~155 a day on validation, ~280 on test). |
| 9 | **Five candidates, simplest first, default settings:** Dummy, port lookup, logistic regression, decision tree (depth 4), gradient boosting | One model; a tuning search; deep learning | Each answers one question: the floor; "is a rule enough?"; "is a linear model enough?"; "are readable rules enough?"; "what do non-linear patterns add?". The brief asks for a simple model, and no tuning keeps the comparison fair. | Some accuracy may be left on the table. Depth 4 keeps the tree readable (15 rules) but catches only 23% inside the budget: its leaves are too mixed. |
| 10 | **One threshold per model:** the lowest validation score with a false-positive rate of at most 0.01% | 0.5; the F1-best threshold; class weights or resampling | The budget, not the model, decides where the line is, and the threshold handles the 20% minority class directly. Scores mean different things in each model, so each gets its own threshold. | Scores rank flows but are not calibrated probabilities (the API calls them "score"). Tied scores can leave budget unused: boosting uses 15 of ~157 false alarms a day on validation. |
| 11 | **Selection rule:** highest validation recall inside the alert budget, among models that meet the speed budget; recall within 0.1 point is a tie, won by the simpler model | Highest PR-AUC; best test result | Written before looking at test, so the test result cannot steer the choice. Result: gradient boosting, 96.5% on validation, 4.7 points above the port lookup. | The tie margin (0.1 point, ~80 bad flows) is a judgment call; it did not matter this time. |
| 12 | **Revised after review.** Gradient boosting with `l2_regularization=1.0` | The default (`l2_regularization=0`); turning off early stopping | Looking at the highest-scored flows showed **88 benign TCP/9200 (Elasticsearch) flows at exactly 1.0**: without regularization the boosting steps ran away on near-pure benign groups. They were 88 of 94 test false alarms (~470 a day, 3x the budget). With `l2_regularization=1.0`: 7 false alarms (~35 a day) at the same recall. Found in an earlier version. | One non-default setting to explain; it is a standard guard against overconfident scores. |
| 13 | **Check before trusting the test number:** repeated vs new flows, a time-based check, false alarms by protocol/port, permutation importance | Trust the random-split test | A good test score is not proof. The time-based check (train on the first 60% of flows in time order, threshold on the next 20%, test on the last 20%) keeps 99.1% recall but gives ~2,060 false alarms a day, 13x the budget: the threshold was set on a 25-minute burst of benign traffic. Re-tuned on that period, recall is 97.8% inside the budget. | It shows a problem that is not fixed here (thresholds drift), and it shapes the production plan: watch false alarms a day and re-tune on recent traffic. |

## Serving

| # | Decision | Alternatives | Why | Tradeoff |
|---|---|---|---|---|
| 14 | One bundle (pipeline, threshold, version, metrics) loaded **once at startup**; without it, `/health` and `/predict` answer **503** | Load per request; crash at startup | Loading per request would add hundreds of ms. A 503 tells a load balancer not to send traffic, and tells a person to train first. | A server without a model is up but useless, so monitoring must alert on 503s. A joblib file can run code when loaded, so models must only come from a trusted registry. |
| 15 | **Strict typed input:** every field required, counts 0 to 2^32, ports 0-65535, no NaN or infinity. Errors are **422, never 500**, and never echo the input. Extra fields (such as IPs) are ignored | A free-form dict; FastAPI's default 422 | The review found two inputs that caused 500 errors (huge integers, NaN). Not echoing input keeps callers' data out of responses. Flow exporters send whole records, so extra fields are ignored rather than refused. | Counts above 2^32 are refused (real counters stop at 65,535). A typo in an extra field goes unnoticed (the 10 inputs are all required). |
| 16 | Response = `is_outlier` + `score` + `threshold` + `model_version`; `/predict/batch` scores up to 1,000 flows in **one model call** | A yes/no only; one call per flow | The score ranks alerts; the threshold and version make every answer traceable. Batching matters: each call has ~9 ms of fixed cost, so one flow at a time manages ~110 flows a second, while batches of 1,000 reach ~75,000. | Callers must not hardcode the threshold. One bad flow rejects the whole batch, with a 422 that points at it. |
| 17 | Logs: a request id (also returned in `X-Request-ID`), method, path, status and latency; **never the request body** | Log full requests | Enough to trace any request without storing traffic data (privacy, PCI DSS). | A request cannot be replayed from the logs. uvicorn's own access log still adds the client IP, so production must configure it. |
| 18 | API tests run against a **tiny real model** built during the test setup, so they need no data and no trained model | Load the real model; mock the model | The data and the model are not in git, so the tests must pass on a fresh clone and in CI. A real pipeline exercises the real preprocessing, and a mock would not. 12 tests run in under a second, including a train/serve parity check. | The tests check the API's behaviour, not the real model's accuracy (that is `src/train.py` and notebook 02). |

## Production design

| # | Decision | Alternatives | Why | Tradeoff |
|---|---|---|---|---|
| 19 | **Serving-only container** (`python:3.12-slim`, pinned serving requirements, non-root user). Today the model is copied in; in production the container loads the approved model from a registry at startup. CI runs `pytest -q` only | One image with every package; building the image in CI | A small image has less to patch, and versioning the code and the model separately makes rollback one step. The model file is not in git, so CI cannot build a working image. | Docker was not installed on the machine this was built on, so the image itself is untested; an earlier version ran the same serving files in a fresh Python environment. |
| 20 | An **LLM agent after the model** (the agentic reviewer): it works on incidents, never in the scoring path, and humans approve any blocking | LLM scoring of flows; no LLM | Scoring needs milliseconds, low cost and repeatable answers. An LLM helps where people are slow: gathering evidence and explaining an incident to an analyst. | It cannot find attacks the model missed, because it only sees flagged traffic. Its value must be proven in shadow mode first (`docs/agentic_review.md`). |
